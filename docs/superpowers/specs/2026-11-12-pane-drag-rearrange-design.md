# pane 끌어 옮기기 — 설계 문서

- 날짜: 2026-11-12
- 상태: 승인됨 (구현 계획: `docs/superpowers/plans/2026-11-12-pane-drag-rearrange.md`)
- 범위: pane header를 끌어 같은 창 안의 다른 자리로 옮긴다. 놓기 전에 그림자 상자로 놓일 위치·크기를 보여 준다.
  이를 위해 pane 배치 모델을 "열 목록(`rows`)"에서 "자유 분할 tree"로 바꾼다.
- 동작 기준: `docs/superpowers/specs/2026-11-12-pane-drag-rearrange-prototype.html`
  (사용자가 직접 끌어 보고 "모두 좋아"라고 승인한 프로토타입. 영역 판정과 크기 계산이 이 파일의 JS에 그대로 있다.)
- 선행 문서: `docs/superpowers/specs/2026-05-18-multi-window-design.md`(창·세션 구조)

## 1. 목표와 동기

지금은 pane의 자리를 바꿀 방법이 없다. 자리를 바꾸고 싶으면 pane을 닫고 원하는 자리에서 새로 열어야 하는데, 그러면
그 안에서 돌던 셸과 에이전트가 사라진다. pane을 살려 둔 채로 손으로 끌어 원하는 자리에 놓을 수 있게 한다.

사용자 요구(원문 요지):

- 타이틀(header) 부분을 끌어서 이동을 시작한다.
- 놓기 전에 어떤 위치에 어떤 크기로 놓일지 미리 보여 준다. 터미널 내용이 아니라 그림자 상자 같은 형식으로 위치와 크기만.
- 사용자가 일반적으로 예상하는 놓는 자리를 지원한다. 예: 긴 세로 pane의 아래쪽으로 끌면 그 pane이 위아래 2분할.
  두 pane 사이로 끌면 그 사이로 들어간다.
- 위아래로 쌓인 두 pane 중 위 pane의 오른쪽 가장자리에 놓으면 **그 pane만** 좌우로 나뉘어야 한다
  (지금 열 구조로는 전체 높이의 새 열이 생겨 버린다 — 이것이 모델을 바꾸는 이유다).

성공 기준:

- header를 잡고 끌면 원래 pane은 흐려지고, 놓을 수 있는 곳 위에서는 그림자 상자 하나가 그 pane이 놓인 뒤 차지할
  **정확한** 위치·크기로 나타난다. 놓은 뒤의 실제 frame이 상자와 어긋나지 않는다.
- 놓는 자리 네 가지(5.3)가 프로토타입과 같은 영역·같은 결과로 동작한다.
- 옮겨진 pane의 셸·에이전트·스크롤백은 그대로 살아 있다(NSView 재배치만 한다, 프로세스는 건드리지 않는다).
- 끄는 동안에는 어떤 pane도 크기가 바뀌지 않는다(PTY에 SIGWINCH가 가지 않는다). 크기는 놓은 순간 한 번만 바뀐다.
- 옮긴 배치와 사용자가 경계선(divider)으로 바꾼 크기가 앱을 다시 켜도(session.json), ⌘K로 프로젝트를 다시 열어도
  (WorkspaceRecord) 복원된다.
- 클릭만 하면(끌지 않으면) 지금처럼 그 pane에 포커스가 간다.

## 2. 비목표

- 다른 창으로 옮기기, 창 밖으로 끌어 새 창 만들기. (멀티 윈도우 설계의 비목표를 그대로 둔다.)
- 여러 프로젝트가 섞인 ALL 뷰에서 끌기. 이 뷰는 저장된 배치를 무시하고 자동 균등 그리드로 그리므로(4절) 옮길
  자리가 의미가 없다. 이 뷰에서는 header를 끌어도 아무 일도 일어나지 않는다(클릭 포커스는 그대로).
- 최대화(⌘↵) 중 끌기. 보이는 pane이 하나뿐이다.
- 크기를 균등으로 되돌리는 명령(경계선 더블클릭 등). 필요해지면 후속으로 한다.
- 놓을 때의 이동 애니메이션. 지금처럼 즉시 다시 배치한다.
- 키보드만으로 pane 옮기기.

## 3. 하면 실패인 것

- 미리보기에 터미널 내용(스냅샷 이미지 등)을 그리는 것. 사용자가 분명히 원하지 않았다.
- 미리보기 상자와 놓은 뒤 실제 위치·크기가 다른 것. "미리 보여 준다"의 의미가 없어진다.
- 끄는 동안 relayout을 돌려 PTY 크기가 흔들리는 것. 에이전트 TUI(claude, codex)가 다시 그리며 화면이 깨진다.
- 클릭 포커스, 터미널 안의 텍스트 선택·더블클릭 단어 선택이 망가지는 것(`Pane.onPaneClicked` 주석의 과거 사고 참고).
- 예전 형식으로 저장된 session.json·WorkspaceRecord를 읽지 못하거나, 새 형식 파일을 예전 빌드가 읽지 못해 창이
  비어 버리는 것. Debug와 release가 session.json을 함께 쓴다.

## 4. 지금 구조 (근거)

- `Workspace.rows: [[Pane]]`가 배치의 유일한 출처다. 이름과 달리 `rows[i]`는 **열**이다: 바깥 split이 열을 좌우로
  늘어놓고(`isVertical = true`), 각 열 안에서 pane을 위아래로 쌓는다(`populateColumns`).
- 모든 relayout 끝에 `equalizeSplits()`가 모든 split을 균등으로 되돌린다. 사용자가 경계선을 끌어 바꾼 크기는 다음
  relayout 때 사라진다.
- 여러 프로젝트가 섞인 ALL 뷰는 `rows`를 쓰지 않고 `PaneGridOrder.readingOrder` + `equalRowSizes`로 균등 그리드를
  만든다(`populateEqualGrid`). 프로젝트 뷰와 프로젝트가 하나뿐인 ALL 뷰만 `rows`를 그대로 보여 준다.
- ⌘D(메뉴 "Split Row" → `splitRow`, `.row`): 포커스된 pane의 열 바로 오른쪽에 전체 높이 새 열.
  ⌘⇧D(메뉴 "Split Column" → `splitColumn`, `.column`): 포커스된 pane의 열 **맨 아래**에 붙인다.
  (단축키 패널 설명 "Split horizontally (add to same row)" / "Split vertically (new row)"는 예전 가로 행 시절 이름이라 지금 화면과 맞지 않는다.)
  ⌘T 등(`.balanced`): `BalancedPanePlacementPlanner`가 가장 덜 찬 열을 골라 붙이거나 새 열을 만든다.
- ⌘[ / ⌘]는 `PaneGridOrder.readingOrder`(열 왼쪽→오른쪽, 열 안 위→아래) 순서로 돈다. ⌘⌥방향키
  (`focusPaneInDirection`)는 화면 좌표로 고르므로 배치 모델과 무관하다.
- 저장:
  - `WindowRecord.rows`(session.json, `SessionAutosaver`) — 창 전체의 열 구조. 복원은 `applySessionLayout`이 열마다
    첫 pane은 `.row`, 나머지는 `.column`으로 `addPane`을 다시 불러 재현한다. `focusedPaneIndex`는 펼친 순서의 index다.
  - `WorkspaceRecord.rows`(⌘K 프로젝트 기록, `WorkspaceAutosaver.records`) — 열마다 프로젝트별 조각으로 나눠 프로젝트
    기록에 담는다(키는 canonical path). 복원(`restore(workspace:)`)도 같은 `.row`/`.column` 재생 방식이다.
  - `WindowRecord.restorable(instance:)`가 다른 instance의 hc pane을 `rows`에서 빼낸다.
- 다른 프로젝트의 pane은 `hiddenPaneParkingView`에 frame을 유지한 채 숨겨 둔다(PTY 크기 보존).
- relayout은 `installRootSplit`에서 모든 pane의 크기 전파를 얼렸다가(`freezeSizePropagation`) 마지막에 한 번 풀어,
  재배치 중 SIGWINCH가 여러 번 가지 않게 한다. 새 배치도 이 경로를 그대로 탄다.
- 칩 끌어 순서 바꾸기(`ProjectFilterBar`, `ProjectOrder.insertionIndex`)가 이 앱의 기존 끌기 구현 예다.

## 5. 사용자 동작

### 5.1 끌기 시작

- pane header(`PaneHeaderView`, 26pt 띠)에서 왼쪽 버튼을 누르고 4pt 넘게 움직이면 끌기가 시작된다.
  그 전에 놓으면 지금과 같은 클릭이다(포커스).
- 끌기를 시작하면 원래 pane은 반투명(약 35%)으로 흐려지고, 커서 옆에 그 pane의 header 글자(프로젝트 / 브랜치)를 담은
  작은 칩이 따라다닌다. 커서는 closed hand.
- 끌리는 pane이 포커스를 받는다(header를 누른 순간 지금처럼 포커스가 간다).
- 끌 수 없는 경우: 보이는 pane이 하나뿐일 때, 여러 프로젝트가 섞인 ALL 뷰, 최대화 중. 이때는 끌기가 시작되지 않는다.

### 5.2 미리보기

- 놓을 수 있는 자리 위에서는 **그림자 상자 하나**만 그린다: 강조색 테두리(2pt) + 옅은 강조색 채움 + 부드러운 그림자,
  pane과 같은 둥근 모서리. 위치·크기는 "지금 놓으면 끌리는 pane이 차지할 최종 frame"이다(5.4의 규칙으로 계산한 결과
  배치에서 그 pane의 frame). 다른 pane이 어떻게 밀려나는지는 그리지 않는다.
- 놓아도 배치가 그대로인 자리(5.5)와 작업 영역 밖에서는 상자를 숨긴다.
- 미리보기는 Workspace 위에 얹은 overlay 뷰에만 그린다. split tree와 pane frame은 끄는 동안 건드리지 않는다.

### 5.3 놓는 자리 (판정 순서대로)

좌표는 Workspace 기준. 상수는 프로토타입 값이다(`OUTER = 16`, `GAPZONE = 14`, `CENTER = 0.3`, 틈 8pt, 바깥 여백 4pt).

1. **작업 영역 맨 바깥 테두리** — Workspace 경계에서 16pt 안쪽. 가장 가까운 변을 고른다.
   결과: 끌리는 pane이 전체 높이의 새 열(왼쪽·오른쪽 변) 또는 전체 너비의 새 행(위·아래 변)이 된다.
2. **두 pane 사이 틈** — 어떤 split의 이웃한 두 자식 사이 틈의 중심선에서 ±14pt, 그리고 그 split의 범위 안.
   여러 후보가 걸리면 중심선에 더 가까운 것, 같으면 더 깊은 split.
   결과: 그 split의 두 자식 사이에 끼워 넣는다.
3. **pane 가운데** — pane을 사방에서 30%씩 들어간 가운데 사각형.
   결과: 끌리는 pane과 그 pane의 자리를 바꾼다. **언제나 켜져 있고 설정 토글은 없다.** (프로토타입의 체크박스는 시험용이었다.
   사용자가 승인한 정리본에 "가운데 = 자리 바꾸기"가 고정 영역으로 들어 있었다.)
4. **pane 가장자리 쪽** — 나머지. pane을 두 대각선으로 나눈 네 삼각형 중 커서가 있는 쪽(왼·오·위·아래).
   결과: **그 pane만** 그 방향으로 둘로 나누고, 끌리는 pane이 그 방향 쪽 절반을 차지한다.

(사이 틈과 바깥 테두리는 pane 안쪽까지 조금 들어오므로 1·2가 3·4보다 먼저 판정된다.)

### 5.4 놓은 뒤의 크기 규칙

배치는 tree(6절)이고 split의 자식마다 비율(weight, 합 1)이 있다. 결과 배치는 "놓을 자리에 끌리는 pane을 먼저 넣고, 그다음
원래 자리에서 뺀다"로 계산한다(넣기 전에 빼면 참조가 무너지는 경우가 있다. 비율 재분배가 비례식이라 결과는 같다).

- **pane 가장자리:** 대상 pane의 몫을 대상과 끌리는 pane이 반씩 나눈다. 대상의 부모 split이 같은 방향이면 그 split 안에서
  나란히 자식이 되고, 아니면 대상 자리에 새 split(대상 + 끌리는 pane, 0.5/0.5)이 들어간다.
- **사이 틈:** 자식이 n개인 split에 끼우면 끌리는 pane이 1/(n+1)을 받고, 기존 자식들은 비율을 유지한 채 n/(n+1)로 줄어든다.
  (모두 같은 크기였으면 끼운 뒤에도 모두 같은 크기다.)
- **바깥 테두리:** 프로젝트 root가 같은 방향 split이면 맨 앞/맨 뒤에 끼우는 것과 같다(1/(n+1)). 아니면 root 전체와 끌리는
  pane을 새 split으로 감싼다(0.5/0.5).
- **가운데(자리 바꾸기):** 두 pane이 서로의 자리·몫을 그대로 가져간다.
- **원래 자리에서 빼기:** 빠진 pane의 몫은 형제들이 비율대로 나눠 갖는다. 자식이 하나 남은 split은 없어지고(그 자식이
  split의 자리·몫을 물려받는다), 같은 방향 split 안의 같은 방향 split은 펼쳐 합친다(비율은 곱해서 보존).

예 (프로토타입 `A | B/C | D`, 열 셋 각 1/3):
- C를 B의 오른쪽에 → `A | B | C | D`, 비율 1/3, 1/6, 1/6, 1/3.
- B를 A와 B/C 열 사이 틈에 → `A | B | C | D`, 모두 1/4.
- D를 A의 아래쪽에 → `A/D | B/C`, 열 각 1/2.

### 5.5 제자리와 취소

- 결과 배치의 **구조**(pane 순서·split 방향·중첩, 비율 제외)가 지금과 같으면 제자리로 본다: 상자를 숨기고, 놓아도 아무것도
  바꾸지 않는다. 예: 자기 자신 위, 자기 바로 옆 틈, 이미 맨 끝에 있는데 그쪽 바깥 테두리, B/C에서 C를 B의 아래쪽에.
  (비율만 달라지는 결과도 제자리로 친다. 사용자 의도가 "옮기기"이지 "크기 바꾸기"가 아니기 때문이다.)
- 자리 바꾸기는 자기 자신이 아니면 언제나 유효하다.
- Esc, 작업 영역 밖에서 놓기 → 취소. 아무것도 바뀌지 않는다.
- 끄는 도중 배치가 다른 이유로 바뀌면(pane이 셸 종료로 닫힘, 새 pane 추가, 필터 전환, 창 크기 변경 등) 끌기를 취소한다.

## 6. 배치 모델 — 프로젝트별 분할 tree

### 6.1 모양

- 노드는 두 종류: pane 잎, 그리고 방향(좌우 `row` / 위아래 `column`)과 자식 목록·자식별 비율을 가진 split.
- 불변식: split의 자식은 2개 이상, 비율 합 1, 자식 split은 부모와 방향이 다르다(같으면 펼친다, 5.4).
- **tree는 프로젝트마다 하나다** (내 결정). 끌기가 일어나는 화면은 프로젝트 뷰와 프로젝트가 하나뿐인 ALL 뷰뿐이고, 둘 다
  한 프로젝트의 pane만 보여 준다. 창 전체 tree 하나를 두고 필터로 가지를 쳐서 보여 주면, 보이는 tree에서 정한 "사이 틈"
  위치나 경계선 비율을 숨은 pane이 섞인 전체 tree로 되돌려 옮기는 규칙이 복잡하고 모호해진다. 프로젝트별 tree면 보이는
  것과 저장된 것이 같다. `WorkspaceAutosaver`도 이미 프로젝트별로 기록한다.
  - Workspace는 `projectId → tree`를 가진다. 프로젝트 순서는 지금처럼 `knownProjectIds`(칩 순서)가 정한다.
  - 프로젝트 뷰 = 그 프로젝트의 tree를 그대로 NSSplitView로 그린다. 여러 프로젝트 ALL 뷰 = 지금처럼 균등 그리드.
- 크기는 비율로 기억한다. 창 크기가 바뀌면 비율대로 늘고 준다. 경계선을 끌면 그 split의 비율을 갱신해 기억한다
  (지금의 "relayout마다 균등" 동작은 없어진다).

### 6.2 기존 동작이 바뀌는 곳

- **⌘D:** 포커스된 pane만 좌우로 나누고 새 pane이 오른쪽 절반 (지금: 오른쪽에 전체 높이 새 열).
- **⌘⇧D:** 포커스된 pane만 위아래로 나누고 새 pane이 아래 절반 (지금: 열 맨 아래에 붙이고 열 전체 균등).
  ⌘D·⌘⇧D가 새 pane을 놓는 방향(오른쪽·아래)은 지금과 같다. 메뉴 제목과 단축키 패널 설명(`KeyboardShortcutsPanel`)을
  실제 동작에 맞게 고친다: "Split Right" / "Split Down".
- **⌘T 등 자동 배치(`.balanced`, 새 pane·hc 고아 pane·`cd`로 들어온 pane):** 지금처럼 균형 잡힌 자리를 알아서 고른다. 요구: tree가 아직 "열들 + 열 안 쌓기" 모양이면
  지금의 `BalancedPanePlacementPlanner`와 같은 결과를 낸다. 그 밖의 모양에서는 가장 넓은 pane을 긴 쪽으로 나눈다
  (같으면 읽는 순서상 앞의 것). 정확한 규칙은 builder에게 맡긴다.
- **pane이 다른 프로젝트로 `cd` — 떠난 자리 기억 (사용자 결정):** projectId는 cwd에서 정해지고(`ProjectIdentity.derive`:
  가장 가까운 `.git` 조상의 basename, 없으면 cwd 자체의 basename), git 저장소 밖에서는 `cd`할 때마다, 저장소 루트에서 `cd ..`만 해도
  프로젝트가 바뀐다. 끌어서 맞춘 자리를 이런 일로 잃지 않게 한다.
  - pane P가 프로젝트 A를 떠나 B로 가면, A의 tree에는 P의 잎을 **"떠남" 표시로 남긴다**(그리지 않는다). A를 그릴 때는 떠난
    잎을 가지치기한 tree(형제들이 비율대로 그 몫을 나눠 가진 모양)를 쓴다. P는 B의 tree에 자동 배치로 들어간다.
  - P가 A로 돌아왔을 때 A에 P의 "떠남" 잎이 아직 있으면 그 잎을 되살린다 — 떠나기 전과 같은 자리·같은 크기. 없으면 자동 배치.
    (B에서 떠날 때는 B에도 똑같이 "떠남" 잎이 남는다.)
  - A의 배치를 손대는 모든 동작 — 끌어 놓기, ⌘D/⌘⇧D/⌘T 등으로 A에 pane 추가, A의 pane 닫기, A의 경계선 끌기 — 은 먼저 A의
    "떠남" 잎을 모두 버리고(보이는 그대로의 tree로 확정하고) 그다음 동작을 적용한다. 그래서 영역 판정·제자리 판정·결과 계산은
    언제나 보이는 tree 위에서만 일어나고, 숨은 잎과 섞인 위치를 되돌려 옮기는 규칙이 필요 없다.
  - pane이 닫히면 모든 tree에서 그 pane의 "떠남" 잎도 지운다. "떠남" 잎은 저장하지 않는다(재시작하면 잊는다, 내 결정).
  - 떠나 있는 동안 A의 이웃 pane들이 그 몫만큼 커지는 것(그리고 그 SIGWINCH)은 지금 동작과 같다.
- **pane 닫기:** 5.4의 빼기 규칙.
- **⌘[ / ⌘]:** 읽는 순서 = 칩 순서대로 프로젝트, 프로젝트 안에서는 tree의 잎을 깊이 우선(앞 자식 먼저)으로. 열 모양
  tree에서는 지금 순서와 같다. 여러 프로젝트 ALL 그리드도 이 순서로 채운다.
- ⌘⌥방향키, hidden pane parking, freeze/thaw는 그대로.

## 7. 저장과 복원

- `WindowRecord`와 `WorkspaceRecord`에 tree를 담는 **선택적(optional) 필드**를 더한다. 잎은 지금의 `PaneRecord`다.
  `WindowRecord`는 프로젝트별 tree들, `WorkspaceRecord`는 그 프로젝트의 tree 하나. 스키마 버전은 올리지 않는다
  (`projectOrder`를 더할 때와 같은 방식 — 예전 빌드가 계속 읽을 수 있어야 한다).
- **`rows`도 계속 쓴다.** 예전 빌드(Debug·release가 session.json을 공유)가 pane을 잃지 않도록, tree를 근사한 열 구조로
  펼쳐 함께 저장한다. 근사 방법(예: 각 프로젝트 root가 `row`면 자식 하나를 열 하나로, 그 밖은 잎 순서대로 한 열)은
  builder가 정한다. 새 빌드는 tree 필드가 있으면 그것만 믿는다.
- tree 필드가 없는 예전 기록은 `rows`에서 만든다: 프로젝트마다 그 프로젝트 pane만 남긴 열 구조를 `row(column(…), …)`로
  바꾸고 비율은 균등. (예전 기록에는 크기 정보가 없다.)
- 복원은 `.row`/`.column` 재생 대신 tree를 직접 세운다. pane 생성(`addRestoredPane`의 id·backend·hook 정보 처리)은 그대로.
- `WindowRecord.restorable(instance:)`는 tree에서도 같은 pane을 빼야 한다(5.4의 빼기 규칙). `focusedPaneIndex`의 의미
  (어떤 순서의 index인지)는 새 형식에서도 저장과 복원이 같은 순서를 쓰도록 맞춘다.
- `WorkspaceAutosaver.records`: 프로젝트 tree에서 그 기록 키(canonical path)에 속한 pane만 남긴 tree를 쓴다. 한 projectId
  안에 키가 여러 개인 드문 경우도 같은 방식으로 가지를 친다.
- 경계선을 끌어 바꾼 비율도 저장 대상이다(autosave 트리거에 포함).

## 8. 구현 메모

정해진 것:

- 끌기는 창 안에서만 일어나므로 pasteboard 기반 `NSDraggingSession`이 필요 없다. header의 mouseDown에서 시작하는 추적
  (mouseDragged/mouseUp, Esc 감시)으로 충분하다. 어느 쪽이든 터미널 안의 클릭·선택 이벤트 경로를 건드리지 않는다.
- 미리보기 overlay는 Workspace 맨 위의 layer-backed 뷰 하나(그림자 상자) + 커서 칩. hit-test에서 투명(`hitTest` → nil).
- 영역 판정과 결과 계산은 AppKit과 떨어진 순수 함수로 둔다(입력: tree, 각 pane·split의 frame, 커서 좌표 / 출력: 놓을 자리,
  결과 tree, 끌리는 pane의 결과 frame). 결과 frame은 실제 NSSplitView 배치와 같은 계산(틈 8pt, 여백 4pt, 비율)이어야 한다.
  프로토타입의 `hitTest`·`applyDrop`·`layout`·`shape`가 기준 구현이다.
- 놓으면 tree를 바꾸고 relayout 한 번. 기존 freeze/thaw 경로로 PTY 크기 변경은 한 번만 간다.

builder에게 맡긴 것:

- tree 타입 이름과 위치, NSSplitView 중첩으로 그리는 방법, 비율 ↔ divider 위치 변환(`setPosition(_:ofDividerAt:)`),
  경계선 끌기에서 비율을 읽어 오는 delegate 지점.
- pane 최소 크기: 결과 배치에서 어떤 pane이든 너무 작아지면(예: 터미널이 몇 칸 안 되는 크기) 그 자리는 놓을 수 없는 곳으로
  다룰지, 그대로 둘지. 정하면 이 문서에 적는다.
- 커서 칩의 정확한 모양, header 위 hover 커서(open hand) 여부.
- ⌘T 자동 배치의 비(非)열 모양 규칙 세부(6.2).
- `rows` 근사 펼치기 방법(7절).

## 9. 검증

- 단위 테스트: tree 연산(나누기·끼우기·바깥 테두리·자리 바꾸기·빼기·펼치기), 영역 판정(경계값 포함), 제자리 판정,
  결과 frame 계산, 예전 `rows` → tree 변환, tree → `rows` 근사, `restorable(instance:)`, ⌘D·⌘⇧D·⌘T 배치(열 모양에서 지금과
  같은 결과), 읽는 순서, 떠난 자리 기억(나갔다 바로 돌아오면 같은 자리·크기 / 그 사이 배치를 손대면 자동 배치 / 닫히면 지움).
  5.4의 예 세 개는 그대로 테스트로 만든다.
- 실제 앱 확인(필수): 단위 테스트만으로는 끌기 배선을 증명하지 못한다. Debug 빌드를 띄워 프로토타입의 두 배치에서 네 가지
  자리를 끌어 보고, 상자와 놓은 뒤 frame이 일치하는지, 끄는 동안 PTY 크기가 그대로인지(에이전트 화면이 다시 그려지지 않는지),
  클릭 포커스와 터미널 텍스트 선택이 그대로인지, 재시작 후 배치·크기가 복원되는지 본다.
  (이 저장소 메모: 에이전트 세션에서 띄울 때 환경 변수 누수 주의, Debug 빌드는 `-derivedDataPath build/DerivedData-debug`.)

## 10. 내가 정한 것 (사용자 확인용)

대화에서 사용자가 정한 것: header로 끌기 시작, 그림자 상자 미리보기(내용 없이), 가장자리 = 그 pane만 나누기, 사이 틈 = 끼우기,
프로토타입의 네 영역과 크기 규칙 전부, 여러 프로젝트 ALL 뷰·최대화 중 끌기 없음, 다른 창으로 옮기기 범위 밖, ⌘D/⌘⇧D = 포커스된
pane만 나누기, ⌘T = 지금처럼 균형 배치, 경계선으로 바꾼 크기 유지, `cd`로 나갔다 돌아온 pane은 떠난 자리로 복귀
(그 사이 그 프로젝트 배치를 손댔으면 자동 배치, 6.2).

내가 정한 것:

- tree를 창 하나가 아니라 **프로젝트마다** 둔다(6.1). 다른 프로젝트로 `cd`한 pane은 새 프로젝트 tree에 자동 배치로 들어간다.
- 가운데 = 자리 바꾸기는 언제나 켜짐, 설정 토글 없음(5.3).
- "떠남" 잎은 저장하지 않는다 — 앱을 다시 켜면 떠난 자리 기억은 사라진다(6.2).
- 비율만 달라지는 결과는 제자리로 친다(5.5).
- 끄는 도중 배치가 다른 이유로 바뀌면 끌기를 취소한다(5.5).
- 끌리는 pane이 포커스를 받는다. 놓을 때 애니메이션은 없다.
- 저장 형식은 optional 필드 추가 + `rows` 계속 쓰기(7절).
